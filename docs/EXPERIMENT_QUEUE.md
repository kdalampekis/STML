# Autonomous experiment loop: rules, queue and log

A scheduled job reads this file every ~15 minutes. Follow it exactly. Owner's instruction (2026-10-16): keep experimenting until the
game logs are ready; finish (interpret + record) the previous task before starting another; when a result is interesting, queue and run follow-ups.

## Rules for every cycle
1. **Look first.** `pgrep -fl "python.*experiments"`; `memory_pressure | tail -1`; `sysctl -n vm.swapusage`; `ls logs/`.
2. **If a job is running:** check it is making progress (CPU time of the python process rising, log advancing). If it is stalled (memory), kill it, note it in the Log and rerun alone.
   Do NOT start a second GPU job. Then stop the cycle (say in one line what is running and its progress).
3. **If a job finished, complete it BEFORE anything else:** read `runs/<run>/report.md`; compare with the PREDICTIONS written in the script docstring; state plainly which held and which
   failed; mention seed sd and the ~1 point run-to-run noise (differences under 2 points are not interpretable); add a bullet to CLAUDE.md section 7 (with the run folder) and, if it concerns
   a component, to `docs/ARCHITECTURE_V2.md`; run `python -m pytest -q`; update the status table below.
4. **Then pick the next task:** the first `todo` item in the queue, or a follow-up created from the last result (add it to the queue with its prediction BEFORE running).
5. **Before launching:** write predictions + the controls (shuffled / ablation) in the script docstring; >= 3 seeds; use `stml.runlog.Run`; add a unit test for new code; run the script with `--quick`
   first; memory must be >= 40% free; launch detached: `nohup perl -e 'use POSIX; setsid(); exec @ARGV' python experiments/<x>.py > <scratchpad>/x.out 2>&1 &` then
   `caffeinate -i -m -s -w <python pid> &`. Never overwrite a run; never touch `data/raw/` or `logs/`; no git.
6. **Honesty:** report nulls as nulls; never claim an effect inside the seed sd; do not tune on test data; say when a comparison is one of many.
7. **Interesting result?** (effect > 2 points AND > 2 seed sd, or a clear contradiction of a written prediction): queue 1-2 follow-ups that test the mechanism, with predictions, and run them. Do not pile up
   more than 3 todo items.
7b. **Promising result (owner's instruction, 2026-10-16): improve the hyperparameters and test deeper.** After the mechanism follow-up, run a hyperparameter search for the promising method
   (learning rate, width, layers, epochs, weight decay, batch size, and method-specific knobs) using VALIDATION episodes only (random search, >= 12 configs, 2 seeds), then confirm the best vs the default on the
   TEST set with >= 3 seeds, and test deeper (scaling of the key factor, other settings, ablations, harder levels). Report tuned vs untuned honestly; a gain that appears only after tuning on validation and is
   under 2 points or 2 sd is not a finding.
8. **Stop condition (owner, 2026-10-16, replaces the earlier one): do NOT stop when files appear in `logs/`. Stop launching experiments ONLY when the owner writes "game logs ready"; then let the running job finish and run the game-log analysis (task L: `python scripts/analyze_game.py logs/`). Until then keep experimenting, including OUT-OF-THE-BOX ideas aimed at the bottlenecks of the architecture (data-limited feedback learner, proof depth, large worlds, noisy teachers, small-effect asking/memory), drawing on the papers in `literature/` and the thesis.**
9. Add one line to the Log at the bottom each cycle that does something (date/time, what).
10. The loop's output goes to the owner: keep each message short (what finished, what the result means, what runs now).

### Q1 spec (write the script from this)
Hidden-premise episodes as in `stml/model/logic_episodes.py` (50% visible). Per episode: a candidate pool of M = 20 claims, a budget of B = 8 asks (the verdict of each asked claim is revealed and added to the graph, 'fb' mode),
then the learner judges 10 held-out claims of the same world. Policies for choosing the next claim: `random`; `entropy` (largest predictive entropy of the current feedback model); `margin` (smallest top-2 margin);
`infogain` (exact greedy oracle: the claim whose revealed verdict makes the most held-out claims knowable, using `knowable`). Same trained feedback model for all policies (train once on random asks). Metric: accuracy on the
held-out claims after B asks, and the learning curve over asks. PREDICTIONS (write in the script): infogain > entropy >= random by >= 2 points at B = 8; entropy is not better than random by more than the seed sd
(uncertain claims are mostly unknowable ones, which teach little).
